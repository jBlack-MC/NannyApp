# Android, web and API audit — 25 October 2026

Scope: the current working tree, including existing uncommitted changes. Reviewed authentication, authorization, nanny verification, booking transitions, uploads, subscription gating, Android networking/session/navigation, routing, and existing security tests. No application fixes were made. No production login, destructive probe, or real payment was attempted. This is a source audit with isolated regression checks, not a certification of the hosted deployment or distributed APK.

## Prioritized findings

### 1. Critical if active: published administrator credentials

Evidence: `README.md:65–84` explicitly directs readers to hosted demo accounts and includes an administrator password. `NannyApp.Web/admin/verifications.php:3–17` grants that role actual verification privileges, rather than a read-only demonstration role.

Anyone with the README can use those credentials if they remain active. This potentially exposes user administration, private verification documents, and payment-ledger decisions. The audit did not attempt the live login, so current credential validity and exposure to real data are unverified.

Fix: disable or rotate the published accounts, revoke their existing sessions, remove passwords from documentation, and isolate public demonstrations from real users and data. Removing the current README value alone does not invalidate copies or Git history.

### 2. High: API profile edits bypass nanny re-verification

Evidence: `NannyApp.Mobile/NannyApp/api/nannies/profile.php:12–22` changes biography, experience, skills and qualifications without changing verification status. The equivalent web update deliberately changes `verified` to `pending` in `NannyApp.Web/nanny/profile.php:82–87`.

Reproduction: start with a verified synthetic nanny, update qualifications through `PUT /api/nannies/profile.php`, then read the profile. It retains its verified badge and remains eligible under `require_booking_slot()` despite changes that the web client sends for admin review.

Fix: put profile mutation and verification invalidation in a shared transactional service used by both clients. Add a regression asserting that both paths invalidate approval for the same fields.

### 3. High: uploads can exhaust storage; replaced avatars are retained

Evidence: `NannyApp.Shared/config/storage.php:93–121` applies the total quota only to local storage. S3 bypasses it; database storage checks individual file size only. `NannyApp.Mobile/NannyApp/api/user/upload_avatar.php:12–34` stores each new image and overwrites the reference without deleting or queuing deletion of the old file. The endpoint has no upload rate limit. Portfolio uploads also lack account-level quotas.

A single authenticated account can repeatedly upload valid images. On local storage this can consume the shared quota and block everyone else's uploads; on database/S3 storage it can keep increasing storage and cost. Database storage is the default when `VERCEL` is set. This was established from the code; no exhaustion test was run.

Fix: enforce atomic per-account and global quotas across all drivers, rate-limit uploads, queue deletion of superseded images after successful replacement, and clean up new objects if the database write fails.

### 4. High deployment risk: registration treats unproven email addresses as verified

Evidence: `NannyApp.Shared/config/security.php:46–49` requires verification only when `NANNYAPP_REQUIRE_EMAIL_VERIFICATION` is exactly `1`. Otherwise `NannyApp.Mobile/NannyApp/api/auth/register.php:42` and `NannyApp.Web/auth/register.php:53` insert `email_verified = 1` without sending proof-of-ownership email.

With the default configuration, anyone can register an unclaimed address belonging to someone else and use the resulting account as verified. Enabling verification later does not repair these already-verified records. This is an intentional prototype setting in comments, but it is unsafe for a real-user deployment.

Fix: default production to verification required; keep email ownership separate from permission to use an unverified prototype account. Audit and reverify accounts created while the bypass was enabled. Current hosted environment settings were not inspected.

### 5. Medium: pending bookings can monopolize a nanny's calendar

Evidence: `NannyApp.Shared/config/bookings.php:69` treats pending requests as blocking conflicts. `create_booking()` at line 75 has no per-parent limit or expiry for pending holds. Both `api/bookings/create.php` and `NannyApp.Web/parent/book.php:156` call it without a booking rate limit.

An eligible parent can create requests for many separate future slots without payment and prevent other parents from booking them until the nanny rejects each request. No automatic pending-hold expiration was found in the reviewed workflow.

Fix: define a short expiry for tentative holds, cap outstanding requests per parent/nanny, and apply shared rate limits. Ensure expired holds stop participating in conflict checks atomically.

### 6. Medium: remember-me cookies have no server-side expiry

Evidence: `NannyApp.Web/auth/login.php:50` sets a 30-day browser cookie. `NannyApp.Web/includes/functions.php:82` restores authentication by matching the raw `remember_token`, with no expiry condition. The schema has no remember-token expiry column. `NannyApp.Shared/config/security.php:68–72` stores the raw token.

The browser expiration is not a server-side validity boundary: a copied token can be manually replayed after 30 days until logout, password change, replacement, or another explicit revocation clears it. Database read exposure also yields a directly reusable credential.

Fix: persist a token hash and expiry, enforce expiry on every restore, rotate after use, and invalidate legacy tokens during migration.

### 7. Medium: CSRF validation accepts missing tokens

Evidence: `NannyApp.Web/includes/functions.php:58–65` compares `$_SESSION['csrf'] ?? ''` with `$_POST['csrf'] ?? ''`. Both missing values become equal empty strings. The duplicate API-side helper has the same implementation.

Confirmed dynamically in the project's PHP 8.3 test image: loading the real web helper, setting both arrays empty, and calling `verify_csrf()` returned normally. This is relevant to a direct login POST in a fresh session, before a form GET generates a token; it permits login CSRF using an attacker's account credentials. Existing authenticated sessions with a nonempty token still reject missing tokens; this is not a universal authenticated-action bypass.

Fix: require both values to be nonempty strings of the expected format before using `hash_equals`. Test direct POSTs without a prior form request, not only wrong tokens after rendering a form.

### 8. Medium: Android/API discovery includes suspended and unverified nannies

Evidence: `NannyApp.Mobile/NannyApp/api/nannies/search.php:8` requires only the nanny role. Verification is an optional caller-controlled filter at line 40, and there is no active-status filter. Android's `NannySearchFilters` in `domain/model/Models.kt:238` defaults `verifiedOnly` to false. The detail endpoint likewise lacks a target-account status check.

Normal Android search can show pending/rejected profiles, and even `verified_only=true` can return a suspended nanny whose profile remains verified. The booking service correctly rechecks eligibility, so this finding is about unsafe discovery and continued profile exposure, not a demonstrated booking authorization bypass.

Fix: enforce active and verified eligibility on server-side public discovery. Permit owner/admin inspection separately, with explicit rules for historical booking participants.

### 9. Medium: search bypasses Plus-only profile fields

Evidence: `NannyApp.Mobile/NannyApp/api/nannies/detail.php:32–47` hides qualifications and specialisations from non-Plus viewers. `api/nannies/search.php:75` returns those same fields to every authenticated caller.

Reproduction: use an ordinary parent token to search for the nanny, and compare the returned fields with the locked detail response. Client-side hiding cannot protect fields already present in the search JSON.

Fix: share an entitlement-aware serializer or omit extended fields from all discovery responses. Test the same non-Plus viewer across list and detail endpoints.

### 10. Medium functional defect: Android Google sign-in has no backend

Evidence: `app/src/main/java/com/nannyapp/ui/auth/LoginScreen.kt:92` exposes Google sign-in; `data/api/AuthApi.kt:30` calls `auth/google.php`. There is no such endpoint in `NannyApp.Mobile/NannyApp/api/auth/`, and the Vercel router resolves actual PHP files. `app/build.gradle.kts:71` also defaults the client ID to a placeholder without release validation.

The flow cannot complete against this repository's backend, even if credential acquisition succeeds on the device.

Fix: hide the button until configured and implemented, or add server-side identity-token verification, explicit account-linking rules, role restrictions and release configuration validation. Test the complete device-to-backend flow.

## Additional hardening and functional observations

- Android stores its 90-day bearer credential as an ordinary DataStore string (`SessionManager.kt:22,90`; API `_bootstrap.php:56`). Backup is disabled and app sandboxing protects normal access, so this is not an unauthenticated remote exploit. Keystore-backed encryption would reduce exposure after app-data extraction; consider shorter-lived credentials with rotation.
- Android's global Coil image loader attaches the bearer token to every image request (`NannyApplication.kt:57–60`), without checking origin. Current uploaded-media URL generation uses the application origin, so an attacker-controlled external-image injection was not established. Restrict authorization to the configured API origin before future content or image-provider changes make this exploitable.
- Android always navigates new registrations to the verification screen (`NannyNavGraph.kt:86`), which claims an email was sent even when the backend bypasses verification. Branch on the server's actual verification state and delivery result.
- Subscription entitlement reads trust the last stored status until expiry (`NannyApp.Shared/config/subscriptions.php:38–43`). The reviewed code refreshes purchases through a client-triggered endpoint; no independent revocation/refund reconciliation was found. Add server-driven reconciliation before relying on this feature commercially. Live Play configuration and refund handling were not tested.
- Web logout accepts GET and revokes all sessions (`NannyApp.Web/auth/logout.php:4–9`), allowing a cross-site top-level navigation to sign a user out across devices. Use POST with CSRF protection for global revocation.

- Ran `python tests/docker-checks.py` using its disposable MariaDB stack. The test container reported all requested checks passed and exited 0, including HTTP authentication, authorization, booking operations, migrations, media, cache and mail regressions.
- Ran `python tests/docker-checks.py --postgres`. The test container reported all PostgreSQL migration and cross-client integration checks passed and exited 0.
- PowerShell marked redirected Docker progress on stderr as `NativeCommandError`; the outer tool invocations returned 1 despite the successful test-container results. The pass statements above refer to the actual suite logs, not an assertion that every wrapper exit was clean. Both disposable stacks were removed by their wrappers.
- Independently reproduced missing-token CSRF acceptance in the built PHP image. No database, real account or external request was used for that probe.
- Ran `gradlew.bat --no-daemon :app:assembleDebug :app:testDebugUnitTest :app:lintDebug` with the installed JDK 21. BUILD SUCCESSFUL in 4m 37s; 60 tasks, 3 executed and 57 up-to-date. Unit-test and lint-analysis tasks reused Gradle's up-to-date results; this was not a forced clean rerun or physical-device test.
- Did not verify live credentials, hosting environment flags, S3 bucket ACLs, real email delivery, Play billing, physical-device behavior, or the published APK's match to source. No dependency CVE review was performed.

Recommended order: isolate published admin access, unify nanny verification policy, bound uploads, enforce truthful email verification, then address booking abuse and session/CSRF defects. Add regression coverage for these findings; passing the existing suites does not establish that these paths are secure.
