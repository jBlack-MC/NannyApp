3. Integrity and lifecycle rules

  • InnoDB foreign keys link profile, child, booking, payment, message and review ownership.
  • Booking creation/rescheduling locks the nanny row, validates every selected child and checks overlap in the same transaction.
  • Booking and ledger state changes commit with notification events; failures roll back together.
  • The recorded payment amount is the historical price source; later nanny-rate edits do not alter prior bookings.
  • Migrations are ordered, checksummed and advisory-locked. Production uses the CLI runner and never destructive seed imports.

5. Data contracts

Response envelope

{ "success": true|false, "message": string|null, "data": object|array|null }. Errors use appropriate 400, 401, 403, 404, 405, 409, 429 or 503 status codes.

Booking representation

Includes IDs/reference, participant names, date/time, duration, address/location, notes/children details, status, agreed hourly rate/amount, authorized PIN visibility, check-in/out timestamps, dispute data, payment/payout status and created time.

Authentication

Authorization: Bearer <opaque token>. Only a token hash is stored. API clients must treat 401 as session loss and clear account-scoped local data.

Uploads

Multipart media is MIME/size checked and stored under generated private keys. Bytes are returned only after role/ownership checks. Android image selection is limited to 5 MiB before upload.
