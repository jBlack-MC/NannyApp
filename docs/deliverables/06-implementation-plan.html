1. Current baseline

The repository already contains the PHP web portal, Android app, shared business services, MariaDB migrations, private storage abstraction, automated synthetic checks, an APK download endpoint, an admin action centre and AWS pilot configuration. Local PHP/JavaScript/PWA/cache/download checks, disposable MariaDB migration/booking regressions, HTTP security checks, Android assembly, seven JVM tests and lint passed on 10 October 2026.

Open evidence: the AWS stack is not created; the production container build was blocked locally by Docker clock drift; live mail, DNS/TLS, backups, signed APK and physical-device acceptance remain unverified.

2. Delivery phases and indicative timeline

Phase 0 — Decisions and accounts · 1–2 days

Confirm domain, owner/operator, support details, email sender, retention policy, recovery objectives and AWS budget alarms. Use Stockholm eu-north-1.

Phase 1 — Production hardening · 2–4 days

Resolve Docker clock, build image, review environment defaults, validate CloudFormation, remove demo data, approve legal/safety copy and complete remaining release review.

Phase 2 — AWS staging · 2–3 days

Create EC2/EIP/security group, DNS, TLS, database volumes, secrets and workers. Run migrations and synthetic smoke tests.

Phase 3 — Release validation · 3–5 days

Restore drill, live email, private media, browser/device/accessibility, concurrency and rollback tests. Fix defects and rerun gates.

Phase 4 — Android release · 1–2 days

Build with real HTTPS API URL, sign with protected key, verify SHA-256/install/update and place APK in private release folder.

Phase 5 — Controlled pilot · 2 weeks

Invite a small cohort, monitor queues/errors/feedback daily and review success metrics weekly.

  • GitHub Actions runs isolated MariaDB/HTTP/mail/security tests and Android verification. Resolve the recorded GitHub account billing lock before relying on hosted CI.
  • Build immutable application image; keep credentials, uploads, APK signing key and runtime data outside it.
  • Back up and restore-test before migrations. Run only the shared CLI migration runner.
  • Deploy staging, test, then switch/restart deliberately. Keep the previous image and additive schema for rollback.
  • Do not automatically deploy on every push during the pilot.

5. AWS deployment runbook

  1. In Stockholm, upload deploy/aws/ec2-stack.yml to CloudFormation; review costs before creating.
  2. Point the domain A record to the Elastic IP and restrict SSH to the operator’s /32.
  3. Install Docker on Ubuntu, copy reviewed source to /srv/nannyapp and create protected deploy/aws/.env.
  4. Build; start MariaDB; run migrations; start app, Caddy and workers.
  5. Verify TLS, login, booking, messages, uploads, recovery mail, queues and admin workflows.
  6. Back up, restore-test, enable external checks and alerts, then admit synthetic users.
  7. Build/sign the APK with https://DOMAIN/api/ and publish it as deploy/aws/releases/NannyApp-latest.apk.

8. Definition of done

Production is ready only when code checks pass, CloudFormation and image are validated, HTTPS/domain/email/workers function, migrations and restore are proven, private uploads are authorized and backed up, parent/nanny/admin staging journeys pass, signed APK installs on real devices, policies/support contacts are approved, monitoring is active and rollback has been rehearsed.
