Nanny-App · Product & Engineering

Professional Engineering Audit

Evidence-based review of the web app, Android app, API, database, delivery process and project vision.

Version 1.020 October 2026Status: prototype hardening

1. Executive summary

Overall assessment: 6.2/10. Nanny-App is a functional prototype with substantial implemented scope across web, Android, API and database layers. It is not yet production-ready because live configuration, credential hygiene, physical-device evidence, recovery operations and a small number of test/documentation gaps remain open.

The central vision remains sound: help parents find trusted childcare, help nannies manage care work, and give administrators the controls needed for verification, support and dispute handling. The next stage should prioritise trust and reliability evidence over adding broad new features.

3. Evidence reviewed

  • PHP web app in NannyApp.Web, Android/Compose client in NannyApp.Mobile/NannyApp, shared database/storage layer in NannyApp.Shared, tests, scripts and GitHub Actions.
  • Approximately 31 table definitions and 27 foreign-key relationships, with migration order/checksum documentation.
  • Android configuration using compile SDK 36, min SDK 26 and target SDK 35; a historical build log exists, but the current environment lacks Java/JAVA_HOME for a fresh build.
  • Automated checks passed for syntax and many feature areas, while the full backend suite stopped at tests/security/backend.php with an unverified bearer-policy failure.
  • Existing documentation, release files, deployment plans and live-site configuration were compared for consistency.

5. Project vision update

Trust

Verified care discovery

Protect parent and child information, verify nanny evidence, and make status and support paths understandable.

Reliability

One account across channels

Registration, login, profile data, images and sessions must behave consistently on web and physical Android devices.

Evidence

Demonstrable delivery

Every marked feature needs a reproducible test, device recording or operational proof rather than a documentation-only claim.

Responsible pilot

Safe operations

Manual payment states, private media, support queues, audit logs, backups and rollback remain explicit pilot boundaries.

Vision decision: the next release is a reliability-and-evidence release. Securing configuration, proving the mobile-to-database path, clearing the backend test failure and documenting release gates take priority over broad new features.

6. Updated roadmap

P0 · Immediate

Rotate exposed credentials; remove public demo passwords; align live environment variables; preserve only safe public keys in clients.

P1 · This iteration

Handle duplicate registration races; fix the bearer-policy test; verify mobile registration/login/profile-image upload and readback over HTTPS; add a controlled demo-account procedure.

P1 · Release evidence

Run Android on a physical phone, capture the feature video, validate email verification, run accessibility checks and record database/API/authentication evidence without exposing secrets.

P2 · Operational maturity

Complete restore drill, external monitoring, queue alerts, dependency review, image-storage scaling plan and documentation reconciliation.

7. Change implemented after the audit

Registration conflict hardening completed. Both web and mobile registration endpoints now roll back safely and re-check the email after a failed insert. If another request won the race, the user receives a clear duplicate-account conflict instead of a misleading HTTP 500 response.

This is a small, low-risk first change that improves the account contract for both clients without changing passwords, authentication tokens or database schema. The next recommended change is P0 credential/demo-account remediation, followed by a physical Android media/readback acceptance test.

8. Audit conclusion

Nanny-App is suitable for continued prototype development and assessment demonstration once the known configuration and test issues are clearly labelled. It should not be described as production-ready until the P0/P1 actions above are evidenced. The project has a credible foundation; the immediate goal is to make its trust, reliability and release claims verifiable.
