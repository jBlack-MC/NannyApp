Design Brief

Visual language, interaction patterns, wireframes and inclusive design

Version 1.010 October 2026Status: implementation baseline + launch requirements

1. Creative direction

Nanny-App should feel calm, capable and protective: clear enough for a stressed parent, warm enough for a care marketplace and disciplined enough for verification and dispute work. Use generous whitespace, rounded surfaces and direct language. Trust comes from specific status information and predictable actions, not decorative claims.

Typography

Sora for expressive headings; Manrope for interface copy; system sans-serif fallback for resilience. Use 1.5–1.7 body line-height, 16 px minimum body text, and no more than 70 characters per reading line.

Iconography and imagery

Use simple outlined Material-style icons with visible labels. Photography should show real care contexts with consent, diverse families and no staged safety claims. Never use identity-document imagery decoratively.

3. Component rules

Buttons

One primary action per region; verb-led labels; minimum 44 × 44 px; disabled state explains unavailable APK or action.

Status

Pair colour with text/icon. Use consistent pending, confirmed, in-progress, completed, disputed and cancelled labels.

Forms

Persistent labels, examples for dates/times, inline errors connected with ARIA, preserve user input after safe validation errors.

Tables

Responsive horizontal region, sticky context where useful, semantic headers and action labels that identify the record.

5. Responsive behavior

320–599 pxSingle column; bottom navigation in Android; stacked actions; horizontally scrollable data tables; no hover dependency.
600–899 pxTwo-column cards when content permits; comfortable touch spacing; side panels become sheets or full-width sections.
900 px+Multi-column dashboards, persistent navigation and broader comparison tables while maintaining readable line lengths.
Large text / zoomNo clipped labels at 200% zoom; controls wrap; content remains usable without horizontal page scrolling.

6. Accessibility requirements

  • Target WCAG 2.2 AA: contrast, keyboard operation, focus visibility, meaningful order, labels, error identification and 44 px pointer targets.
  • Every image has purposeful alternative text or an empty alt attribute when decorative.
  • Do not expose a secret PIN to screen previews or unrelated roles; announce state changes without repeating sensitive values.
  • Respect reduced-motion preferences and never require animation to understand progress.
  • Test keyboard-only, TalkBack, VoiceOver/Safari PWA, 320 px, 375 px, tablet, desktop, dark mode and 200% zoom.

7. Content and trust language

Use “manual payment record”, “held”, “released” and “refunded” only as ledger states. Avoid “charged”, “transferred” or “escrow” until a real payment provider exists. Explain why identity documents are requested, who can access them and when they are deleted. Safety and cancellation content must be approved before launch.
