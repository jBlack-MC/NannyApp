## Confirmed findings

1. **Critical — deployment instructions destroy existing data.** `docs/PRODUCTION_LAUNCH.md:5` instructs importing `NannyApp.Shared/database/schema.sql`; that file's line 9 drops `nanny_app`. Following this on an existing pilot destroys its users, bookings and ledger. **Fix:** replace that instruction with reviewed, versioned, non-destructive migrations and independently verified backups. Follow `PILOT_DEPLOYMENT.md` for this release; never import the development schema into an existing environment.

2. **High, security — a parent can review the wrong nanny.** `api/reviews/create.php:9,13,23,30` accepts `nannyId`, verifies only ownership/completion of `bookingId`, discards the booking row, then inserts and recalculates the supplied nanny's rating. Complete a booking with A and submit B's ID: B receives a review without providing that booking. **Fix:** derive the nanny ID from the authorized booking; reject mismatches and validate an integer rating from 1 through 5 rather than silently clamping it.

3. **High, security — changing a password leaves stolen sessions usable.** `api/user/change_password.php:17` updates the password hash without revoking API or remember tokens. A stolen bearer token remains usable after the victim changes the password. **Fix:** transactionally revoke both token types as password recovery now does; explicitly decide whether to issue a replacement session to the current client.

   **Resolved 2026-09-28:** shared transactional password replacement revokes API/remember tokens and reset links. Web sessions fail their password fingerprint check; Android clears the current account and returns to sign-in. Locked credential rechecks and conditional remember-token writes prevent stale logins recreating sessions. Synthetic HTTP/concurrency/rollback regressions pass.

4. **High, booking/ledger corruption — state transitions race.** `api/bookings/accept.php:10,15,18` reads pending and subsequently updates by ID alone. `api/bookings/cancel.php:8,17,18` separately changes booking and payment state. Accept reads pending; cancel writes cancelled/refunded; accept then writes confirmed: the result is a confirmed booking with a refunded ledger. A failure between cancellation's two writes also splits state. **Fix:** lock the booking in a transaction shared by every transition, recheck its allowed source state and update the ledger in the same transaction. Alternatively use conditional writes with checked affected-row counts where sufficient.

5. **High, ledger corruption — automatic release can release a disputed booking.** `NannyApp.Mobile/NannyApp/includes/functions.php`, `auto_release_stale_payments():493`, selects eligible rows at line 498, conditionally changes the booking at 509 and updates payments at 512 without requiring the booking update to succeed. The web copy has the same pattern in `NannyApp.Web/includes/functions.php`, function at 479 and booking update at 495. If `api/bookings/dispute.php:23` changes the selected booking to disputed between selection and update, the conditional booking update affects zero rows but its payment still becomes released. **Fix:** lock/recheck the booking and ledger together and require a successful transition before release. This currently corrupts the manual-payment ledger; it does not demonstrate a bank transfer.

   **Automatic-release path repaired 2026-09-28:** web/API now share a conditional booking update and ledger write in one transaction. Ineligible candidates cannot release payments, and ledger failures roll back completion. Other manual transition/dispute races remain open under finding 4; this is not full P08/P09 completion.

6. **High, correctness — booking creation trusts invalid eligibility and child IDs.** `api/bookings/create.php:10–16,27–31,49–53` checks a positive nanny ID but not whether it belongs to an eligible nanny. An existing parent account can satisfy the user foreign key and receive a booking with a zero-rate payment because its nanny profile is absent. Nonexistent or other-parent child IDs are silently removed from the query result, allowing a booking with no authorized children. **Fix:** verify an active, verified nanny with a valid profile/rate, require a bounded array of distinct integer child IDs and require every requested child to belong to this parent. Validate future appointment times, finite bounded duration and field lengths.

7. **Medium, request failure — malformed booking input causes uncaught exceptions.** `api/bookings/create.php:21` invokes `nanny_has_booking_conflict()` before its try block; the helper in `NannyApp.Mobile/NannyApp/includes/functions.php:404` constructs `DateTimeImmutable`. A nonempty invalid date throws. With a valid date and `childrenIds: "1"`, line 27 calls `count()` on a string and throws a PHP TypeError. **Fix:** validate JSON field shapes and strict date parsing before calling helpers and return a controlled 400 response. Do not turn ordinary malformed input into a 500.

8. **High, booking correctness — conflict checking is not atomic.** `api/bookings/create.php:21,35,41` checks overlap before beginning the insertion transaction. Two requests for the same available nanny/time can both see no conflict and both insert. `nanny_has_booking_conflict()` in `NannyApp.Mobile/NannyApp/includes/functions.php:403` also restricts conflicts to pending/confirmed bookings, excluding in-progress bookings. **Fix:** serialize booking creation against a stable nanny row, check overlaps inside that transaction using a current locking read, then insert; include all blocking states. Apply the same protocol to web creation and future rescheduling.

9. **Medium, incorrect financial display — history uses today's rate.** `api/bookings/_serialize.php:42` computes amount from the current profile rate, whereas `api/bookings/create.php:51–53` stores the booked payment amount. Raising a rate from R100 to R200 changes a two-hour historical booking display from R200 to R400 while its ledger remains R200. **Fix:** serialize the recorded booking/payment amount and persist the agreed hourly rate if needed for itemization.

10. **Medium, broken messaging — incoming messages are omitted.** `api/messages/thread.php:8,11` binds both OR branches as sender=current user, receiver=other user. The reverse direction is never selected. A synthetic SQLite reproduction with both directions returned only outbound messages. **Fix:** bind `b2` to the other user and `a2` to the current user; test both directions and exclusion of unrelated messages.

11. **Partially resolved 2026-09-28:** password change now returns `{}`; booking cancellation remains open. **Medium, misleading failure — successful empty responses fail on Android.** `android/java/com/nannyapp/util/NetworkResult.kt`, `safeApiCall():24`, rejects a successful null `data`. `api/bookings/cancel.php:23` returns exactly that, while its Android contract expects `Unit`. Password change previously had the same defect and now emits `{}`. Cancellation succeeds on the server but Android reports an error; booking detail may remain stale. **Fix:** explicitly support successful Unit responses while preserving strict data requirements for data-returning calls, or consistently emit `{}` for every Unit endpoint. Add cross-language contract tests.

12. **Medium, blocked UI — booking actions never stop loading after success.** `android/java/com/nannyapp/ui/booking/BookingDetailViewModel.kt`, `runAction():52–54`, sets `actionInProgress=true` then calls `load()`. Neither success nor error in `load():43–44` clears it. After a successful accept/check-out/completion, controls consuming that flag remain disabled until the screen is recreated. **Fix:** await the refresh in the action coroutine and clear the flag in `finally`.

13. **High, release blocker — the Android release points at a placeholder.** `NannyApp.Mobile/NannyApp/app/build.gradle.kts:23` supplies an example API URL; only the debug build overrides it at line 28 with emulator address `10.0.2.2`. The checked-in release configuration cannot connect to the pilot backend; that debug address also does not identify the developer machine from a physical handset. **Fix:** require an explicit validated HTTPS release URL at build time and fail builds with the placeholder. Make the development host configurable; put no credentials into the APK.

14. **Medium, background feature failure — WorkManager's custom factory is bypassed.** `android/AndroidManifest.xml:10` leaves the default initializer enabled, while `android/java/com/nannyapp/NannyApplication.kt:13` implements `Configuration.Provider` and the notification worker (`work/NotificationSyncWorker.kt:22`) needs injected constructor dependencies. The default initializer prevents the intended custom configuration from supplying that factory, so worker construction fails. Existing Android lint also flags this configuration. **Fix:** remove only WorkManager's initializer metadata as described in [Android's custom configuration documentation](https://developer.android.com/develop/background-work/background-tasks/persistent/configuration/custom-configuration), retaining other Startup initializers. Verify actual execution after cold start on a device.

15. **Medium, crash/freeze — file selection reads unbounded content on the UI thread.** `android/java/com/nannyapp/ui/components/FilePicker.kt`, `rememberFilePickerLauncher():25`, calls `openInputStream(...).readBytes()` in the activity-result callback without bounds or exception handling. A very large selected image can exhaust memory; slow cloud-backed content blocks the UI; revoked permission or an I/O failure throws from the callback. **Fix:** perform bounded streaming on `Dispatchers.IO`, enforce the upload size before allocating the entire content, handle permission/I/O failures and cancellation, and validate actual content type.

16. **Medium, online assets fail — cache-write failure discards a good network response.** `NannyApp.Web/service-worker.js:22–25` awaits `cache.put()` inside the same promise chain that catches fetch failures. If storage quota is exceeded and the asset has no cached entry, a successful network fetch becomes `undefined` from `cache.match()`, invalidating `respondWith`. A synthetic Node VM reproduction confirmed this sequence. **Fix:** handle cache writes separately and always return the fetched response; only network failure should invoke offline fallback.

   **Resolved 2026-09-29:** cache-open/write errors no longer discard online responses. Offline cache misses/read failures return a network-error response, never `undefined`. Synthetic regressions cover quota failures, disabled storage, uncached offline assets and migration to cache v11. Real-device testing remains open.

17. **Medium, resource/privacy retention — deleting documents leaves stored objects.** `NannyApp.Web/nanny/profile.php:33–34` unlinks a web-root-relative path even though uploads now live in shared storage or S3, then deletes the database record regardless. `api/nannies/portfolio.php:53–54` deletes only the record. Deleting a portfolio entry therefore leaves orphaned private documents. The new media authorization prevents access through the removed record, but storage retention and cost remain. **Fix:** persist a deletion job containing the authorized storage key before removing its row; retry storage deletion and reconcile failures.

18. **Medium, ambiguous successful mutation — notification failure produces a 500 after booking commit.** `api/bookings/create.php:54,60` commits before calling `notify()`; `NannyApp.Mobile/NannyApp/includes/functions.php:244` inserts the notification without containing database errors. If that insert fails, the user sees a failed request even though a booking exists. **Fix:** insert a durable notification event in the booking transaction and dispatch separately; add a per-user creation idempotency key so a lost response can be retried and return the original booking.

## Resilience and a realistic next feature

The next feature considered is **rescheduling a confirmed booking while preserving its agreed price and manual-payment adjustments**.

| Component/coupling | Concrete user impact | Smallest useful change |
|---|---|---|
| Single shared database | Outage prevents authentication, booking changes and messaging across both frontends; cached Android reads cannot accept new bookings. | Keep one database at pilot scale, add internal readiness checks, encrypted off-host backups and a measured restore drill. Choose acceptable recovery time/data loss with the team before promising availability. |
| Booking writes followed by inline notifications | Notification storage failure can make an already committed booking look unsuccessful. | Transactional notification outbox plus idempotent booking creation; do not make provider availability part of request success. |
| Account email delivery | A provider/worker outage blocks new verification and password recovery. | The implemented optional Resend outbox bounds network calls and retries; monitor oldest pending job and worker failures. Existing accounts need not stop browsing while mail is delayed. |
| One upload volume | Losing the volume loses portfolio evidence and photos even if bookings survive. | Persistent storage outside releases plus encrypted off-host backups and a restore check; adopt private object storage when volume or multi-host deployment justifies it. |
| Duplicated web/API booking commands | Rescheduling would need matching overlap, state, price and ledger changes in both implementations; today's races demonstrate the risk of divergence. | Extract only shared transactional booking commands, starting with transitions and overlap checks. Keep HTTP parsing and serialization in each frontend. Store the agreed price, not a reference to today's profile rate. |
| Inconsistent API empty-success contracts | Adding another rescheduling action can repeat the Android false-failure bug. | One explicit Unit-response contract and a small set of client/server contract tests. |

If only three architecture changes fit: **(1)** shared transactional booking commands, because conflicting bookings and incorrect ledger state affect the core service; **(2)** idempotent creation plus transactional notification events, because interrupted requests must not mislead users or duplicate mutations; **(3)** monitored backup/restore and readiness, because a single database failure otherwise stops the entire pilot with an unknown recovery time. Replication and a rewrite are not prerequisites for these changes.
